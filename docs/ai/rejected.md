# 被否决的 AI 建议

[docs/ai/index.md](index.md) 是**全部**对话的原始记录——包括被采纳的。这一份是它的补集：
**哪些 AI 提出的东西被明确否决了，以及否决的理由。**

留这份记录是因为：一份只展示"AI 提了什么、我照做了"的记录，证明的是我会用工具；
只有"AI 提了什么、我为什么不照做"才能证明我在做判断。

每一条都能在 `docs/technical_design.md` 或对应的 ADR 里找到落点——这里是索引和理由，
不是第二份真相。

---

## 一、被否决的架构模式

这些在设计阶段被逐条讨论过，全部否决，记录在 design §8.6。**重新引入其中任何一个都是
回归，不是改进。**

| 被否决的东西                           | 否决理由                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 领域事件 / 事件总线 / event sourcing   | 单进程顺序管线；一个状态机加一张 `episode_state` 表就够了                                                     |
| CQRS / 读写模型分离                    | 读侧就是几条聚合 SQL                                                                                          |
| Repository 之上再加 Service/Manager 层 | 用例类**本身就是**应用服务，再加一层只是改个名字                                                              |
| ORM（SQLAlchemy）                      | schema 很小，而我们需要对事务和 PRAGMA 的精确控制                                                             |
| 每个值对象配一个 Factory/Builder       | pydantic 的验证式构造器已经足够                                                                               |
| 通用「ETL 框架」抽象                   | 一共四个源。YAGNI。插件点只有一个：`SourcePort`                                                               |
| 把所有本体统一成一个定长向量           | 销毁掉这个项目**唯一**存在理由的那个东西：语义                                                                |
| 摄取时做 min-max 归一化                | 摄取只做保存；归一化是下游关心的事，而且它是训练超参                                                          |
| 用多进程提高吞吐                       | 本轮吞吐不是目标；它换走的是崩溃恢复的清晰性                                                                  |
| EAV / 通用键值 / 无边界的 `extensions` | 把校验推迟到运行时——那就只是名义上有 schema                                                                   |
| 为了凑预算而截断 episode               | 制造出上游根本不存在的边界（见 [答辩 §5.5](../design_answers_zh.md#55-预算是上界不是目标而且不提供截断选项)） |
| web 看板                               | 约 200 个 episode，REVIEW 队列就是一条 SQL                                                                    |

其中最后一条需要限定：**这一轮**不做看板是对的；到 500 个数据集时它是必需的，
理由和形态写在 [答辩 §6.5](../design_answers_zh.md#65-人工复核看板)。否决的是"现在建"，
不是"永远不建"。

## 二、被真实数据推翻的 AI 方案

这一类更值得看：不是"我觉得不好"，而是**跑了之后发现它是错的**。

### 1. 「reward 属于允许有损，只留 episode 级 success 就行」——错

最初的 schema 计划把 `next.reward` 归到"允许有损"。真实数据推翻了它：pusht 的
`next.reward` 是 T 形块与目标区域的**多边形重叠率**，而数据集里根本不存 T 形块的位姿
（`observation.state` 只有推杆的 xy）。**一旦丢弃就永远无法重算。**

行为克隆确实不需要它，但离线 RL 把它当成核心监督信号——**摄取层没有资格替下游做这个
决定**。成本论据也不成立：一帧一个 float，四个源加起来几百 KB。

→ design §2.2d 的"更正"段落。

### 2. 「源 C 的 action 是 7 维（3 位置 + 3 姿态 + 1 夹爪）」——错，是 8 维

第八维是 `terminate_episode`，一个**控制标志位**，不是自由度。而且原来的表格把
"只留 7 维"写得像是无损的。它不是：丢弃 channel 是一次**有损变换**，必须记录在
`provenance.transforms` 里。

→ [ADR 003](../adr/003-oxe-action-vector-is-8d.md)，design §A.C.6。

### 3. 「用 TFDS / TensorFlow 读 RLDS」——否决

TensorFlow 是一个几百 MB 的依赖，只为了读一种容器格式。M0 的 spike 验证后，改成
**130 行标准库直接解析 TFRecord**。副作用是 Python 版本 pin 的上界（3.13）本来是被
TF 逼出来的，现在只剩 spike 还需要它。

→ [ADR 001](../adr/001-rlds-reader-no-tensorflow.md)。

### 4. 「陀螺仪和加速度计合成一个 6 维 IMU 信号」——错，它们是两个时钟

[ADR 011](../adr/011-epic-layered-availability-and-origins.md) §3 最初就是这么写的，
被 [ADR 012](../adr/012-epic-imu-is-two-streams.md) 推翻并取代：在 `P28_101` 上两条流的
时间戳最大相差 15 ms。合成需要重采样，而重采样是不可逆的——**摄取层不做不可逆的选择**。

### 5. 「存 EPIC 的抽帧编号」——反了，要存官方 fps 编号

M4 把 M0 的结论**反了过来**：秒是权威的，帧序号要按**官方** fps 重新推导，
因为那才是 EPIC-Fields 索引位姿用的时钟。抽帧编号原样保留在
`raw_extra.epic.extraction_numbering` 里，两套编号**永不混用**。

→ [ADR 010](../adr/010-epic-two-frame-numberings.md)。

### 6. 「fixture 绿了就可以了」——最贵的一次教训

M4 的所有门禁在 fixture 上全绿之后，**第一次跑真实服务器发现了四个缺陷**，
其中一个已经潜伏两个里程碑、吃掉了 50 个 aloha episode 里的 35 个
（LeRobot 的全局行索引问题）。

结论写成了一条纪律：**fixture 必须是数据「结构」的等比例模型，而不是数据「体积」的
缩小版。**

→ [ADR 012](../adr/012-epic-imu-is-two-streams.md) / [ADR 013](../adr/013-lerobot-global-index-and-qc-history.md)。

### 7. 「QC 阈值凭经验设一个 5 倍」——不可达

`ACTION_JERK` 的第一版拿 `max` 和 `p99.9` 比。M5 测了整个语料的分布，发现这个比值
**从未超过 1.57**——一条 5× 的规则在**任何**输入上都不可能触发。一个永远不会响的告警
比没有告警更坏，因为它让人以为有覆盖。

从此 `config/qc.yaml` 里**每一个阈值都注明它是从哪个实测数字推出来的**，
分布本身由 `uv run rdp stats` 写进 `reports/qc_stats.md`。

→ [ADR 014](../adr/014-qc-thresholds-from-measured-distributions.md)。

### 8. 「为了证明规则有效，造一个 FAIL 出来」——明确拒绝

语料的 FAIL 率是 0%，并且**就让它保持 0%**。手工制造一条坏数据来点亮报表，
是把交付物变成演示品。真正该做的是把"3 条规则从未评估过任何 episode"这件事写进报告
（见 [答辩 §8.2](../design_answers_zh.md#82-11-条规则里有-3-条从未评估过任何-episode)）。

### 9. 「欠额的组把余量还回去时，重新套用上限」——错

`ur5_single_arm` 只有 738 合格帧，配额是 1 606。余量重分配时如果继续守 40% 上限，
等于**为了让表格好看而丢弃真实的训练帧**。上限的作用是防止一个本体挤掉别人；
当没有人再想要这份预算时，它就没有作用了。

→ [ADR 016](../adr/016-balanced-curation-quotas-and-seed.md) §2。

### 10. 「用 50 000 帧预算演示采样策略」——测不出东西

作业给的例子是 50 000。这个语料合格帧只有 41 418 帧，**预算根本没有约束力**，
所有策略都产出同一个文件。M6 的全部证据改在 20 000 帧下取。

**一个不能区分策略优劣的预算，不能用来论证策略。**

### 11. 「写完就算持久化了」——`stream_specs` 从未落库

M5 才暴露的一个 M4 遗留缺陷：`stream_specs` 挂在 `EpisodeMeta` 上，但**从来没有被写进
catalog**。正常路径看不出来，因为对象在内存里是完整的；只有一次 `REDO_NORMALIZE`
之后再 `REDO_QC`，才让 60 个 epic episode 里的 40 个失败。

纪律：**聚合的每一个字段都要持久化，而且要测往返，不是测写入。**

→ [ADR 015](../adr/015-qc-episode-facts-and-persisted-streams.md)。

### 12. 「报告里没测到的耗时先填 0」——违反自己的规矩

M7 之前记录的 run 没有阶段耗时。渲染成 `0.000` 是一个看起来正常的谎。改成显示
**"not measured"**——**绝不零填充**这条规则同样适用于我们自己的遥测数据。

→ [ADR 017](../adr/017-report-vocabulary-and-consistency-checker.md)。

## 三、被否决的工具/呈现方案

### Harbor / ATIF 轨迹查看器

本轮考虑过把 AI 对话记录接进 Harbor（一个 agent trajectory 查看器）来展示。
查过数据之后否决：**VS Code 的导出里根本没有工具的返回结果。**

实测：1936 次工具调用里只有 368 次带结构化参数（`terminal` 340 次、`todoList` 27 次、
`subagent` 1 次），只有 23 次带结构化结果。Harbor 的查看器本质是一个**工具调用步进器**，
接进去大约 81% 的卡片会是空的。

而导出里真正丰富的部分是 1314 段 markdown 叙述和 718 段推理——**静态 markdown 恰好
展示这些**。所以改成 `scripts/render_ai_sessions.py`。

### Makefile

考虑过加 `make setup && make demo`。否决：`uv` 已经是唯一的工具链入口，
再加一层 Makefile 就等于**同一条命令有两处拼写**，而其中一处迟早会变旧。
README 和 `docs/implementation_plan.md` 的验收块里写的是同一串 `uv run` 命令。

### 平行英文 README

否决。理由和上面同构，而且更严重：`README.en.md` 和 `README.md` 是同一批主张的两份
拷贝，其中一份会安静地停止为真。文档语言的边界改成按**读者**划分，
见 [ADR 018](../adr/018-delivery-docs-in-chinese.md)。

## 四、一个总结

回看这 12 条，有一个统一的形状值得说出来：

**几乎每一次关键修正都来自真实数据打脸，而不是来自更周密的思考。**

第 1、2、4、5、6、7、9、10、11 条，全部是在"设计看起来很合理、门禁全绿"之后，
被一次真实运行或一次真实测量推翻的。这不是说设计没用——设计决定了错误发生时
**改一个适配器还是改整个模型**。但它确实说明：

> **一个还没跑过真实数据的 schema 决定，是一个假设，不是一个决定。**
